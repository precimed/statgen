# Testing strategy

`statgen/tests` should use `pytest`. MATLAB/Octave validation should be done
with Octave; installed Octave is a prerequisite for tests that exercise MATLAB
functionality. R validation should be callable from pytest when R is available,
while CRAN-facing package tests live in the R package.

## Fixture generation and storage

Fixtures are generated by a standalone script at `tests/fixtures/generate.py`
and committed to the repository. The script is the authoritative description of
what each fixture contains and how it was constructed; running it regenerates
all fixtures deterministically.

Canonical source fixtures under `tests/fixtures/` are committed (not generated
at test time) so that:

- `pytest` runs immediately in CI without a prerequisite step;
- Python, Octave, and R tests read the exact same on-disk bytes for portable
  formats and paired runtime-native files for LD;
- binary fixture contents (LD distribution files, BIM files) are stable references that
  can be inspected independently of the test suite.

To regenerate fixtures after a format change, run:

```sh
python tests/fixtures/generate.py
```

R package `inst/extdata/` fixtures that are exact portable-format duplicates of
canonical files under `tests/fixtures/` are derived copies, not independent
fixture sources. Commit these copies so a fresh checkout supports native R
package builds and tests without a preparation step. Regenerate them with
`make prepare-r-fixtures` when canonical fixtures change.
Repository R package test/build targets must prepare those
copies before invoking R package tests or `R CMD build`, and repository pytest
should verify that the prepared copies match their canonical sources.

Binary arrays in fixtures must use explicitly documented dtypes and byte-order
where the object format exposes them. For LD `.npz` fixtures this means the
CSC component dtypes from [ld.md](ld.md).

Session-scoped pytest fixtures in `conftest.py` may produce derived or computed
outputs in a temporary directory. Tests may also generate on-the-fly temporary
inputs for non-contract scenarios per the fixture growth policy below.

## Fixture growth policy

`tests/fixtures/` is reserved for canonical, contract-critical source files.

Tests MUST add or expand checked-in fixtures only when at least one applies:

- the scenario defines or validates a portable format contract (on-disk bytes,
  columns, or metadata);
- Python, MATLAB/Octave, and R must validate the same exact source bytes;
- the case is a stable regression anchor for a previously fixed bug.

Tests MUST use on-the-fly temporary inputs for:

- malformed input and parser/validator failure cases;
- combinatorial or stress boundary cases where exact source bytes are not part
  of the public contract;
- transient perturbations of canonical fixtures (for example truncating one
  binary array to test length validation).

Implementation-plan fixture sourcing decisions belong in the relevant plan under
`dev/` and must remain consistent with this policy. For R-specific work, use
`dev/impl_R.md`.

Concrete baseline fixture composition (for example exact chromosome count,
fixture sizes, and object mix) is implementation-scoped and should be defined in
the relevant implementation plan, not in this spec.

## Cache schema compatibility fixtures

Routine cache behavior should be tested with temporary files: load canonical
source inputs, save a cache with the current writer, load it back, and compare
the resulting object to the canonical source-loaded object. These tests validate
current round-trip behavior, not historical compatibility.

When an object spec promises support for an older public cache schema, tests
MUST include a checked-in legacy cache fixture produced by the old schema writer.
Such fixtures are stable regression anchors for on-disk cache bytes and are an
explicit exception to the canonical-source-only wording above. They must not be
regenerated by the current cache writer because doing so would stop testing
backward compatibility.

Checked-in cache compatibility fixtures MUST use the flat path convention:

```text
tests/fixtures/cache/<object>_<runtime>_<schema>.<ext>
tests/fixtures/cache/generate_<object>_<runtime>_<schema>.<ext>
```

`<object>` is the object family, such as `reference`, `sumstats`,
`annotations`, or `genotype`; `<runtime>` is the runtime cache family, such as
`python`, `matlab`, or `r`; `<schema>` is the public cache schema identifier
converted to a path-safe name, such as `annotations_cache_0_1`; and `<ext>` is
the runtime-native cache or generator extension, such as `npz`, `mat`, `rds`,
`py`, `m`, or `R`.

Each cache fixture MUST have a schema-specific provenance generator next to it
under `tests/fixtures/cache/`. The generator is the authoritative record of how
the stable bytes were produced. Generators MUST be runnable from the repository
root unless their file header and `tests/fixtures/cache/README.md` explicitly
document a different workflow. A generator may invoke an older release, require
checking out an old tag, or document manual steps that cannot be executed by the
current implementation. Cache fixture generators are not part of the routine
`tests/fixtures/generate.py` regeneration path and MUST NOT be run by
`make fixtures` unless the object spec explicitly redefines the schema fixture
as current, reproducible output.

Legacy cache compatibility tests MUST validate the loaded object's logical
behavior against the canonical portable source fixture for the same scenario.
They should also assert any schema-specific migration behavior documented in the
object spec, such as synthesized metadata fields, dtype/class promotion, sparse
representation, or required rejection behavior when an older loader encounters a
newer schema.

Cache compatibility fixtures are per runtime and per public cache schema because
cache formats are language-specific accelerators, not cross-language interchange
formats. Tests should not require Python, MATLAB/Octave, and R caches to have
identical bytes or to load each other's cache files unless an object spec
explicitly documents such portability.

MATLAB/Octave cache fixtures use the `matlab` runtime path for the `.mat` cache
contract. Repository CI writes and validates these fixtures with Octave because
Octave is the standard MATLAB compatibility proxy. The fixture provenance must
record the writer runtime, writer version when available, and `.mat` format
option. When MATLAB is available through the opt-in `STATGEN_MATLAB=1` path,
tests should also validate that MATLAB can read the same fixtures. If MATLAB
cannot read an Octave-written fixture, or if MATLAB-written and Octave-written
cache bytes differ in a way the object spec treats as contract-relevant, pause
and revise the object spec or split the fixture paths into `matlab` and `octave`
explicitly.

## Octave test harness

Octave tests are wired into pytest from Phase 0. The test suite must be able to
run without Octave and skip Octave-specific tests cleanly.

`conftest.py` at the `tests/` root provides:

- a session-scoped `octave_available` fixture that probes `shutil.which("octave")`;
- a `pytest.mark.octave` marker registered in `pyproject.toml`;
- a `skipif_no_octave` skip decorator for use in test functions.

Octave is invoked via `subprocess` with the `matlab/` directory added to the
path:

```python
subprocess.run(
    ["octave", "--no-gui", "--eval",
     "addpath('matlab'); <test expression>"],
    ...
)
```

Phase 0 must include at least one Octave smoke test that invokes a minimal
`+statgen` function and verifies the return value, confirming that the path
setup and package resolution work end-to-end before any real logic is added.

## Cross-language consistency

Python, Octave, and R loaders should read the same portable source files where
the object contract is portable. LD is runtime-native: Python and R read
`.npz` files, while Octave reads converted `.mat` files derived from those
`.npz` sources. R `.npz` distributions include an R reference-cache sidecar.
Loaders should report matching:

- dimensions;
- vector values;
- reference shard/panel ordering;
- sparse LD matrices and aligned `a1freq` vectors;
- genotype metadata and selected genotype slices through the public on-demand
  accessor;
- binary and continuous annotation matrices, annotation metadata fields, and
  LD-weighted annotation arrays within numeric tolerance.

Cache conversion tests should verify that native cache outputs match portable
source files, not that caches match each other directly. LD converter tests
should verify that MATLAB/Octave `.mat` distributions and R direct `.npz`
loading match the Python `.npz` handoff files at the logical shard level.

## End-to-end alignment invariants

End-to-end tests MUST include a generated synthetic PLINK2 workflow that
checks global alignment across reference, genotype, LD, Python,
MATLAB/Octave, and R runtimes. The primary invariant is:

```text
LDPanel.a1freq == a1 frequency recomputed from
GenotypePanel.fetch_genotypes for the same genotype payload and sample subset
```

This comparison is a global alignment check: allele frequency acts as a compact
checksum of each SNP's genotype vector under the selected sample subset. It is
intended to catch row-order drift, panel-global versus shard-local index errors,
incorrect source-row mapping, chrX subject-subset mistakes, allele-key matching
errors, and sparse LD/reference misalignment that may not be visible from
shape or checksum checks alone.

The end-to-end suite MUST first include a simple chr1-only pre-flight case
where reference, genotype, and LD variants are identical. This baseline checks
PLINK2 conversion, `a1freq`, selected LD `r`, and `multiply_r2` consistency
before the suite introduces cross-shard, chrX, and partial-overlap indexing
cases.

This invariant MUST be checked for autosomes and for chrX sex-specific LD
shards. Autosomal frequencies use diploid observed calls. chrX `female`
frequencies use present female subjects with diploid denominator; chrX `male`
frequencies use present male subjects with haploid denominator. Optional chrX
`combined` checks use the sum of observed ploidy values as denominator.
Unknown-sex subjects may contribute to autosomal checks but must not contribute
to sex-specific chrX checks.

Synthetic end-to-end data MUST be generated from VCF/PSAM through PLINK2
`--make-bed`, not by hand-writing PLINK BED payloads. Test setup must verify
that PLINK2 preserved the intended allele contract after conversion: BIM `a1`
matches VCF `ALT`, BIM `a2` matches VCF `REF`, and marker names remain unique
and traceable. PLINK2 frequency and LD commands must use `--keep-allele-order`.

The generated data MUST exercise re-indexing rather than merely matching
identical files. A recommended pattern is a larger master variant set with two
PLINK2 `--extract` subsets: one for `GenotypePanel` loading and one for
`LDPanel` construction, with a controlled partial overlap. Tests should include
shards `1`, `2`, and `X`; non-sharded and sharded genotype inputs; a chrX FAM
subset in a different order from the autosomal FAM; and variants present only
in one derived panel.

At least one same-position allele cluster MUST be present per shard: multiple
variants sharing `chr:bp` but carrying distinct `(a1, a2)` pairs. Clustered
variants should have distinctive genotype payloads and frequencies, and their
ordering should force matching by `(bp, a1_hash64, a2_hash64)` rather than by
row position or marker name. Tests should fail if sorting or matching keys
disconnect genotype payload rows from their variants.

End-to-end LD `r` checks SHOULD be selective rather than full-matrix
recomputations. Tests should recompute Pearson `r` from fetched genotype
vectors for a small set of sentinel pairs covering positive correlation,
negative correlation, sparse omission below threshold, and chrX sex-specific
differences. `LDPanel.multiply_r2` should be compared against an explicit
per-shard `elementwise(ld_r .^ 2) * M` calculation for small deterministic
vector and matrix inputs.

Use these numerical tolerances for end-to-end comparisons unless a test
documents a stricter precision source:

- `a1freq`: absolute tolerance `1e-5`;
- selected LD `r`: absolute tolerance `1e-3`;
- `multiply_r2`: absolute tolerance `1e-5` for float64 comparisons and `1e-4`
  for float32 comparisons.

Cross-runtime tests compare numeric values within tolerance, not dtype identity.
PLINK2-dependent end-to-end tests should skip cleanly when PLINK2 is not
available.

## Edge cases and failures

Tests should also cover:

- reference checksum computation and `ReferencePanel.is_object_compatible`
  mismatch reports;
- LD load/validation failures when the manifest-declared reference cache has
  shard checksums incompatible with LD shard metadata;
- LD manifest/per-file metadata agreement and sparse payload validation;
- chrX LD shard files, including sex-specific default selection;
- sharded (`@` template) versus single-file loading behavior;
- malformed source files with missing required columns;
- summary-statistic `p` handling for missing values, `0`, negative values, and
  values greater than `1`;
- exact BED/reference chromosome matching, interval boundary behavior,
  continuous annotation value painting, multi-column annotation loading,
  numeric overlap rejection, binary overlap union behavior, loader-declared
  binary status, language-native `value_columns` indexing, generated annotation
  metadata, direct annotation metadata, and metadata sidecar handling including
  mixed sidecar/generated metadata batches;
- mismatch fixtures proving that `statgen` does not normalize aliases such as
  `chr1` to `1` or `23` to `X`;
- genotype metadata alignment, cache round-trips, missing-source masks, ploidy
  vectors, and selected on-demand genotype slices.

## Allele swap matching

Python, MATLAB/Octave, and R tests must cover both matching modes in
[reference.md](reference.md#source-to-reference-matching), including identical
ID-mode exclusions, ambiguity decisions, orientation, and cache round-trips.
The following cases describe genomic-position matching:

- exact and reversed SNV source alleles aligned to a reference following the
  REF/ALT contract, including `A/T` and `C/G`, reference-order output, and
  independence from sumstats source row order;
- reciprocal source SNVs accepted with the exact row winning, including when
  its optional statistics or genotype calls are missing;
- `load_reference` rejects duplicate ordered keys and reciprocal SNVs;
  cache-loaded references are trusted without repeating source validation;
- matching rejects multiple exact source candidates or, absent an exact match,
  multiple eligible swapped candidates; unmatched sumstats duplicates are
  ignored, and swapped candidates do not make a retained exact match ambiguous;
- opt-in indel swaps, disabled by default, with reciprocal reference/source
  keys remaining distinct, exact matches taking priority across all rows, and
  no source-row reuse; verify that disabled indel swaps leave reversed-only
  candidates unmatched with an `info` count;
- variants with both alleles multi-base retaining exact matches but never
  matching through swap fallback, for either value of `allow_indel_swaps`;
- sumstats transformations, missing values, absent optional fields, and
  unchanged exact matches;
- integer and floating genotype fetches, repeated SNP requests, absent
  subjects, missing calls, chrX/ploidy scaling, BED overrides, swap flags,
  shard subsetting, and `/0.2` cache round-trips;
- legacy `/0.1` genotype caches preserving stored mappings and fetching with
  all-false swap state, using the committed historical fixtures;
- nonzero swap-related counts at `info`, suppressed at `quiet`,
  separate strand-ambiguous swap counts, no reports for superseded reciprocal
  rows, and disabled-indel counts only for still-unmatched reference slots;
- numeric matching preserving all 64 hash bits without lazy allele-string
  decoding.

ID-mode coverage must also include:

- palindromic and multi-base exclusions, including exact multi-base matches;
- all four allele orientations, distinct equivalence groups under one ID,
  and the resulting value transformations and diagnostic counts;
- panel-wide reference-key exclusions, including cross-chromosome duplicates,
  and source ambiguity even when candidate values agree;
- unusable IDs at length and character boundaries, literal `NA` and `0` IDs,
  and exact case-sensitive comparison;
- missing-P filtering before candidate counting, ignored or absent sumstats
  coordinates, and genotype chromosome scope;
- invalid matching modes and incompatible `allow_indel_swaps` settings.

## Success criteria

The library is complete when univariate LDSC-style preparation and bivariate
genetic-correlation preparation can be expressed using only public loaders,
accessors, `LDPanel.multiply_r2`, `fast_prune`, and plain arrays. Tests should
exercise at least loading reference, LD, annotations, and one or two sumstats
objects; computing an LD-weighted annotation matrix; applying one random
`fast_prune` mask; and deriving bivariate `z1 * z2` arrays. Python,
MATLAB/Octave, and R should produce matching fixture outputs for those
workflows.

## Test boundaries

Tests should cover `statgen` behavior, not upstream harmonization. Input test
fixtures should satisfy the assumptions of the selected matching mode and the
shared allele-syntax contract.
